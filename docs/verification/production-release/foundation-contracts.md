## FoundationStore (src/lib/persistence/contracts.ts)
Owner + generation bound per request. Obtain a NEW store for every request, not after wiping within an old request. All methods async. PostgreSQL RPC writes are service-role-only; browsers cannot mutate authoritative progression/quota even in their own rows. Account RLS permits own snapshot/quota/card reads; Guest access goes only through verified server routes. No auth schema alterations.
- `read(collection,key)`, `readById(collection,id)` => snapshot|null; collections coaching/discovery/pivot. Snapshot `{id:uuid,revision,data}`.
- `write({collection,key,expected,next,receipt?})`: expected null means create-if-absent (returns existing winner). Update requires same ID + exact revision, next revision+1. Explicit reset uses expected old ID + revision null, NEW ID + revision1. Receipt UUID+server fingerprint prevents conflicting intent reuse; replays return current authoritative snapshot. Reset fences old handles. Do not send client-authored progression as next.data.
- `wipe()` atomically clears owned snapshots, cards, batches, quota receipts and previous-day quota counters; increments generation, permanently revokes Guest capability. For an account owner it keeps only today's numeric daily counters (`used`; pending reservations released) so a wipe cannot renew evaluate/proposal/card allowances; a revoked Guest keeps none (a replacement Guest is a new owner and starts a fresh allowance — accepted cookieless-churn risk, bounded only by admission limits). New account requests may start new work. In-flight old stores cannot resurrect wiped data. Minimal owner/generation tombstone remains for revocation; Supabase Auth identity is NOT deleted/revoked by project-data wipe. Signed-in browser explicit wipe also clears its valid Guest capability's data; logout never erases work.
- `cardQuota()` => day/used/reserved/remaining/freeRemaining/extraRemaining/resetAt. 5 free +30 extra per database Bangkok day, not per topic. Pending reservations reduce available capacity, not successful usage.
- `beginBatch({requestId,fingerprint,count})`: stable UUID for one intent, server fingerprint of canonical input; count1–5. Reserve before AI. If remaining<5 request min(5,remaining); handle concurrent429 by reload/retry. Only `claimed:true` may invoke model. In-flight duplicate =>same lease, claimed:false; return pending UI, do NOT generate twice. Completed same-key retry replays accepted snapshots, even on another day. Changed input/count =>409.
- `completeBatch(leaseId,candidates)`: validates each card, accepts only unique ID + normalized title/problem, atomically persists snapshots and charges accepted count (no fillers). This is exact-content screening, NOT semantic novelty verification: successor card service must also handle semantic repetition and truthful AI source. Invalid/duplicate candidates charge zero. Never call complete with gateway fallback/fixture output.
- `failBatch(leaseId)`: explicit known failure releases reservation, no charge. Known-failed intent stays failed; a user retry may use a NEW intent. Unknown worker failure recovers after bounded expiry: reservation released on next access, same intent may claim a NEW lease; old worker's lease is rejected. Completed receipts are not expired/reissued. `leaseExpiresAt` permits truthful retry messaging. No transaction spans AI network calls.
- `listCards({limit:1..100,cursor?})`: owner-scoped immutable accepted snapshots; opaque nextCursor pagination. Use for seen-card context; do not duplicate storage.
- `quotaStatus('evaluate'|'proposal')`, `consumeQuota({kind,requestId,fingerprint,count?})`: limits5/2, Bangkok day, atomic/idempotent; different count/fingerprint same key =>409. Pivot must NOT consume proposal allowance; repair successor owns policy and progression integration.
- `allowRequest('auth'|'coach')`: distributed admission before network work. Coach12/owner/min +60 global/min; auth6/owner/10min +30 global/min. Global ceiling bounds rotated Guest capabilities without collecting IP addresses. Conservative fixed limits; production tuning needs explicit policy review. Rate metadata expires; wiping project data does not reset the global guard.
Errors: PersistenceError status400/404/409/410/429/503, generic machine code. Provider/SQL/secret error messages never returned. Failures/unknown commits must not cause an automatic new intent; retry stable request ID.
