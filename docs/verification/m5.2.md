# M5.2 — BOM budget estimator & competition calendar

## Implementation scope

- `/bom?projectId=…`: React/Tailwind mobile cards with learner-entered material name, integer quantity, unit price in ฿, editable school-substitute unit price, a labeled `role="switch"`, add/edit/delete with deletion confirmation, and sticky total/budget/savings summary.
- Optional `Project.bom` is backward compatible with existing Guest Projects. Writes use the existing validated local store. Proposal/Plan edits preserve BOM. Switching Projects loads the selected Project's saved records; a URL specifying a missing Project shows an empty state, never another Project's editor.
- Budget comparison uses `Interview.constraints.budgetBaht` from the **current Interview**, explicitly labeled in the UI. No new per-Project budget or constraint schema is invented. Missing budget is not treated as zero; zero is a valid budget. Costs are estimates entered by the learner, not supplier quotes. Item/substitute prices allow 0–1,000,000 baht, at most two decimal places; quantity 1–9,999; at most 200 items, unique IDs. Ordinary money totals sum integer satang to avoid false over-budget from floating-point addition.
- Substitution uses the alternative **per-unit** cost only when selected. Zero represents free borrowing; a more expensive alternative produces an explicit increased-cost message rather than claiming savings.
- A failed storage write leaves the saved list unchanged and retains the form draft for retry. Project selection is disabled while a form is open to prevent silently discarding that draft.
- Invalid stored BOM fields are isolated from otherwise valid Projects. Reads keep the original raw storage document untouched and show a recovery warning. Before the next explicit write, that original is saved under `edtech:bom-recovery`; if backup fails, the write aborts. The normal PDPA namespace wipe removes this backup too. This is recovery isolation, not automatic reconstruction of malformed line items.
- `/calendar?projectId=…`: four sourced competition cards (YSC, NSC, ศิลปหัตถกรรม, ISEF), live calendar-day countdown from today in **Asia/Bangkok**, approximate month ranges and prominent warnings. Past ranges roll forward to a **planning projection**, not an asserted future official date. Inside a range, the countdown is to its approximate month-end, not an application deadline. No “registration open” status is inferred.
- Sources and corrections to the old unverified YSC/NSC month examples are documented in `RESEARCH.md §11`. ISEF is explicitly an international event season requiring prior qualification, not direct registration; ศิลปหัตถกรรม varies by area, including earlier-than-example dates.
- Contextual Project tools connect Proposal, BOM and Calendar without overcrowding the existing six-item mobile shell. The calendar link opens the **same Project's Plan tab** using `/proposal?projectId=…&tab=plan`; projections never overwrite that Plan's deadline.
- No AI request, login, new PII field, secret, backend dependency or new package is required by either feature.

## Self-review and limits

- Standards pass initially found two integration issues: malformed BOM could invoke the pre-existing whole-state reset path; calculator budget cap differed from canonical Constraints. Both were reproduced with failing tests and fixed. Canonical `BomItem` now lives in domain types.
- Spec pass found no BOM/calendar feature omissions, but raised offline hard reload. That was a stronger condition supplied in the review prompt, **not this card's acceptance requirement**. Existing PWA explicitly says it still needs internet, and upstream service worker does not cache routes. This card does **not** claim network-disconnected hard reload/navigation support; its logic and loaded-screen edits are local and independent of AI configuration.
- Calendar estimates are not official competition dates, compliance/eligibility advice or evidence that applications are open. Teacher/organizer confirmation for the correct year/area remains required.
- No live AI, login/cloud-sync, supplier-price validation, push or deployment was performed. Upstream release/security findings were not remediated here.
- Implementation completes only this phase, releasing the existing downstream M5.3 card. Scheduled independent final review remains a separate phase; no duplicate same-card review request.
